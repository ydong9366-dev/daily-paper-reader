## 摘要
大语言模型日益被部署为通过浏览器与网络交互的自主代理。尽管最近的进展由评估端到端任务成功率的基准所推动，但这些评估在很大程度上忽略了真实网页浏览中两个基本的困难来源：对丰富用户界面的复杂操作，以及对动态渲染内容的视觉感知，尤其是在跨多个网站的工作流程中。我们提出了CAP，这是一个可扩展的基准，用于评估浏览器代理在跨站点、类人的网页任务上的表现，这些任务需要复杂的UI交互和视觉理解。具体而言，我们采用分解-重组流水线：先将每个网站抽象为一个结构化站点卡片，捕获面向用户的功能、复杂的执行操作和感知需求；然后将这些组件重组为现实的跨站点工作流程。因此，每个任务都以每个网站上的多个具体操作为基础，从而实现细粒度的诊断。在此框架基础上，我们在严格的质量控制下构建了420个任务，涵盖108个真实网站和24个领域。使用我们可验证的“代理即裁判”评估框架对最先进的浏览器代理进行的实验显示，其成功率较低，并揭示出感知密集型交互仍是一个主要瓶颈，暴露出当前代理与真实世界网页浏览需求之间的巨大差距。

## Abstract
Large language models are increasingly deployed as autonomous agents that interact with the web through browsers. While recent progress has been driven by benchmarks that evaluate end-to-end task success, these evaluations largely overlook two fundamental sources of difficulty in real web browsing: complex actions over rich user interfaces and visual perception of dynamically rendered content, especially in workflows that span multiple websites. We introduce CAP, a scalable benchmark for evaluating browser agents on cross-site, human-like web tasks that require non-trivial UI interactions and visual understanding. Specifically, we adopt a decomposition-and-recomposition pipeline that first abstracts each website into a structured site card capturing user-facing functions, complex execution operations, and perceptual requirements, and then recomposes these components into realistic cross-site workflows. Each task is therefore grounded in multiple specific operations on each website, enabling fine-grained diagnosis. Built on this framework, we construct 420 tasks across 108 real-world websites and 24 domains under careful quality control. Experiments on state-of-the-art browser agents using our verifiable agent-as-a-judge evaluation framework show low success rates and reveal that perception-heavy interactions remain a major bottleneck, exposing substantial gaps between current agents and real-world web browsing demands.

  - **跨站工作流**：真实任务常需要跨多个网站完成信息收集、比较与综合，但现有基准或只评估单站交互，或仅对最终答案评分而不对底层交互难度进行系统测量。
- **论文含义**：现有基准的评估结果无法揭示代理在实际使用中"为何失败"以及"如何失败"，对代理能力的诊断粒度不足。CAP 基准试图弥合这一缺口，为浏览器代理提供一个涵盖跨站工作流、复杂执行操作和挑战性视觉感知的可扩展评测框架。

## 2. 论文提出的方法论

### 2.1 核心思想：分解-重组（Decomposition-and-Recomposition）

CAP 将网站抽象为结构化"站点卡片"（Site Card），再将站点卡片组合成真实、连贯的跨站任务，使每个任务都扎根于每个网站的具体操作，支持细粒度诊断。整个流水线分为四个阶段：

### 2.2 阶段一：站点卡片注释（Site Card Annotation）

- 定义了 24 个功能簇（如电商、旅行预订、学术搜索、房产、代码托管、视频流媒体等），依据 SimilarWeb 排名筛选出 139 个候选网站，排除阻止自动化访问或强制登录的网站后保留 108 个。
- 每个网站 w 被注释为站点卡片 $s_w = \langle F, A, P \rangle$：
  - **F（功能集）**：网站面向用户的功能（如房产搜索、房贷计算）。
  - **A（执行项）**：非平凡的交互操作，定义为 $a = \langle u_{comp}, \tau_{act}, f_{assoc} \rangle$，分别对应 UI 组件、动作类型、关联功能。
  - **P（感知项）**：需要视觉理解的元素，定义为 $p = \langle u_{comp}, \tau_{perc}, f_{assoc} \rangle$。
- **分类体系构建**：以 Ant Design 组件库为基础（约 99k GitHub Stars、超 350 万周下载量），由三位 Web 开发领域专家迭代识别出 64 种动作类型和 56 种感知类型（完整分类见附录 C）。
- **自动注释**：使用开源浏览器代理 Browser-Use 自动探索网站、识别功能并编制站点卡片。最终 108 张站点卡片覆盖 1,167 个功能，实例化了 58/64 种动作类型（90.6%）和 50/56 种感知类型（89.3%）。

### 2.3 阶段二：聚类采样（Cluster Sampling）

- **功能亲和力矩阵 M**：通过 LLM 评估聚类对的协同工作流合理性（如"学术搜索"与"代码托管"亲和力高，"房产"与"代码托管"亲和力低）。
- **步骤 1——锚点选择**：选择历史使用频率最低的聚类作为锚点，$C_{anchor} = \arg\min_{C_i \in C} h(C_i)$，防止常见领域过度表示。
- **步骤 2——亲和力引导扩展**：基于亲和力矩阵和共现统计，LLM 选择 3–6 个与锚点配合良好但较少组合的聚类，增强任务多样性。

### 2.4 阶段三：任务提案（Task Proposal）

- 利用站点卡片中的功能 F 作为构建块，LLM 将跨站功能组合成合理的工作流，生成 600 个任务提案。
- 每个提案 $t_{prop} = \langle u_{intent}, o_{prop}, \phi_{prop} \rangle$ 包含三个部分：
  - **用户意图 $u_{intent}$**：谁需要该任务及原因；
  - **计划输出 $o_{prop}$**：用户期望获得的内容；
  - **信息流 $\phi_{prop}$**：数据在网站之间如何传输，建模为有向无环图（DAG），支持五种基本模式：顺序（Sequential）、并行（Parallel）、扇出（Fan-out）、扇入（Fan-in）、链式（Chain）。
- **质量筛选**：8 名标注员审查所有提案，依据两条标准：(i) 用户意图反映真实需求而非牵强组合；(ii) 跨站信息依赖在执行过程中动态获取而非预设。标注员间一致性高（Cohen's κ = 0.81），512 个提案（85.3%）通过审查。

### 2.5 阶段四：任务实例化（Task Instantiation）

将抽象提案实例化为具体可执行的基准任务 $t_{inst} = \langle d_{desc}, \phi_{inst}, E, o_{inst}, m_{meta} \rangle$，包括：自然语言描述 $d_{desc}$、具体信息流 $\phi_{inst}$、覆盖点集合 $E = E_{act} \cup E_{perc}$、预期输出 $o_{inst}$、元数据 $m_{meta}$。

- **目标导向引出原则（Goal-Oriented Elicitation）**：任务描述以用户目标表达（如"找到 2000 美元以下的公寓"），而非 UI 操作指令（如"拖拽价格滑块"）。
- **输出字段设计**：每个输出字段承担三种验证角色之一——用户价值（User Value）、条件验证（Condition Verification）、来源溯源（Provenance），确保交互可以通过输出间接验证。
- **鲁棒性策略**：优先使用范围过滤而非最高级排序；使用相对时间而非绝对日期；为动态内容提供回退指令；显式指定数量；在任务描述末尾集中放置输出要求。
- 人工审查（理性、复杂度、可执行性、可评估性、主题安全）后，最终确定 420 个任务实例（192 个公开，228 个私有）。

### 2.6 可验证的"代理即裁判"评估框架（Verifiable Agent-as-a-Judge）

解决了两个挑战：最终答案准确性无法反映代理在复杂 UI 操作或感知推理上的具体困难；以及为数百个异构任务手动编写评估脚本代价过高。

- **阶段一：评估脚本生成**：以任务描述和覆盖点为条件，LLM 生成 Python 评估脚本。受两个构件约束：API 白名单 Ω（限制为预定义的安全验证原语）和参考模板 R（固定脚本结构骨架）。执行失败触发自我调试循环，随后通过自反思阶段对照常见边界问题清单验证逻辑正确性。
- **阶段二：Rubric 树构建**：每个评估脚本实现一棵有根树 G = (V, E)：
  - **叶子节点**（$V_{leaf}$）：原子标准，返回二进制分数 $s(v) \in \{0, 1\}$；
  - **内部节点**：聚合子节点分数；
  - **根节点 $v_{root}$**：任务最终分数。
  - 叶子节点分三类：**动作节点**（$V_{act}$，验证复杂 UI 操作）、**感知节点**（$V_{perc}$，验证视觉信息提取）、**其他节点**（$V_{other}$，验证格式等一般要求）。
  - 节点标记为**关键节点**（critical，失败则父节点分数归零）或**非关键节点**（允许部分得分）。
- **阶段三：得分计算**：评分采用"门控后平均"（gate-then-average）策略：

$$s(v) = \begin{cases} 0 & \text{if } \exists u \in K(v): s(u) < 1 \\ \bar{s}_N & \text{if } \forall u \in K(v): s(u) = 1 \text{ and } N(v) \neq \emptyset \\ 1 & \text{otherwise} \end{cases}$$

其中 $\bar{s}_N = \frac{1}{|N(v)|} \sum_{u \in N(v)} s(u)$。任一关键子节点失败即"门控"将零分数向上传播，非关键子节点在关键前提满足后贡献平均值。

- **四个报告指标**：
  - **部分完成率（Partial Completion）**：所有任务根节点分数的均值，捕捉分级进展；
  - **成功率（Success Rate）**：所有节点分数均为 1 的任务比例，捕捉端到端任务成功；
  - **动作分数（Action Score）**：$V_{act}$ 上叶子分数的均值，隔离执行能力；
  - **感知分数（Perception Score）**：$V_{perc}$ 上叶子分数的均值，隔离感知能力。

**发现 1：当前最强浏览器代理在复杂执行与感知任务上表现不佳。**
- 所有系统的成功率都很低：最佳代理 Manus 仅达 8.0%，人类基线也仅 10.0% 完全成功。
- 人类基线部分完成率为 35.0%，归因于任务设计（2–14 个网站、平均 7 个复杂操作、4 个感知挑战）和严格的完美分数标准（要求每个执行、感知、格式叶子都满足）。
- Comet 是异常值：部分完成率领先（48.0%），但成功率仅 6.0%，输出长度比其他代理高一个数量级（104k vs. 3–8k tokens），说明中间推理正确但未能整合成满足所有 rubric 叶子的最终答案。

**发现 2：感知是比执行更严重的瓶颈。**
- Complex-A 上 Comet 领先（67.0%），但所有系统在 Complex-P 上均大幅下降（Comet 58.0%，其他 23.0–34.2%）。
- 五个商业代理和 GPT-5 骨干在 Complex-A 上均高于 Complex-P，而人类基线基本平衡（35.0% vs. 34.0%）。
- 结合发现 4 中"数值读取"（Value Reading）接近零分（0.000），表明对渲染内容的视觉推理是当前代理的主要失败模式。

**发现 3：延长的推理与任务进展相关，但没有代理匹配人类的思考水平。**
- Comet 生成超 100k 输出 tokens 以取得领先的部分完成率；人类基线平均花费 16.3 分钟。
- 快速响应的代理（Genspark 1.7 分钟、Dia 1.1 分钟）排在部分完成率排名的底部。

**发现 4：细粒度视觉读取和 UI 状态推断是代理失败最严重的地方。**
- 执行操作中，节点操作（0.087）和日期范围选择（0.110）得分最低，两者都涉及对复合小部件的精确指针控制。
- 感知操作中，数值读取（0.000）和展开状态感知（0.092）严重受损。
- 任务难度（分数）不由复杂度数量单调解释：单个图表数值读取步骤就能破坏原本简单的工作流。
