## 摘要
多智能体大语言模型（LLM）系统经常失败，并非因为缺少候选答案，而是因为缺乏一种持久机制来决定当前应信任哪个互不兼容的主张。多数投票、辩论和基于评判的选择方法在输出时并未记录哪个主张获胜、哪个存在争议，或为何后续更新取代了先前结果。我们提出 LatticeMind，一种冲突感知的结构化内存，在写入时处理矛盾。它维护显式的项目状态，应用廉价的符号冲突检查，仅对未解决的语义情况调用 LLM 进行调和。在去除来源名称提示的标签盲 ConflictBank 评估中，LatticeMind 达到 0.97 的准确率，而最强聚合基线为 0.61，配对 McNemar 检验显示差异显著（p<10^{-6}）。消融实验表明，移除检查器或调和器会损失 12 至 14 个百分点的性能。在四个次级规划基准上，结果不一：LatticeMind 在四个基准中的三个上优于朴素合并，但在奖励迭代搜索的任务上并未取代深思熟虑类方法。

## Abstract
Multi-agent LLM systems often fail not for lack of candidate answers, but because they have no persistent mechanism for deciding which incompatible claim should currently be trusted. Majority vote, debate, and judge-based selection choose an output without recording which claim wins, which is contested, or why a later update supersedes it. We present \term{LatticeMind}, a conflict-aware structured memory that handles contradiction at write time. It maintains explicit item status, applies cheap symbolic conflict checks, and invokes LLM reconciliation only for unresolved semantic cases. On a label-blind ConflictBank evaluation that removes source-name hints, LatticeMind reaches 0.97 accuracy versus 0.61 for the strongest aggregation baseline, with the gap significant at $p<10^{-6}$ by paired McNemar test. Ablations show that removing the checker or the reconciler costs 12 to 14 points. On four secondary planning benchmarks the picture is mixed: LatticeMind beats naive merge on three of four, but does not replace deliberation methods on tasks rewarding iterative search.

## 一、核心问题与研究动机

- **核心问题**：多智能体大语言模型（LLM）系统经常不是因为缺少候选答案而失败，而是缺乏一种**持久的机制来决定当前应信任哪个互不兼容的主张**。现有的多数投票、辩论、基于评判者（judge）的选择等方法，在决定输出后，并未记录哪个主张获胜、哪个存在争议、以及为何后续更新会取代先前结果。
- **研究动机**：
  - 现有智能体记忆架构（如 MemGPT、Generative Agents、CoALA 等）覆盖了检索、压缩和反思，但**均未将矛盾处理作为一等公民的内存更新操作**。
  - 现有方法要么将信息压缩成流畅的总结（抹去信任原因和取代关系），要么将所有历史无差别拼接（缺乏抑制机制），均无法为时间推移中的分歧提供持久管理。
  - 论文将问题界定为：**矛盾处理应被视为内存问题，而非答案选择问题**。

## 二、方法论：LatticeMind

- **核心思想**：LatticeMind 是一种冲突感知的结构化内存，在**写入时（write time）**处理矛盾，而非在输出时通过聚合解决。它将每个记忆条目显式建模为 `m = (k, c, ρ, τ, η)`，其中 `k` 为键/路由句柄，`c` 为内容，`ρ` 为证据元数据，`τ` 为时间戳，`η` 为状态（PROPOSED、CONFIRMED、CONTESTED、SUPERSEDED）。
- **三大组成部分**：
    1. **结构化写入（Structured Writes）**：智能体的发现（如 FACT、CONSTRAINT、SUB_PLAN）作为显式记忆条目写入，而非立即扁平化为最终答案。对于软件状态应用，提取归一化状态声明 `z = (u, σ, v, β, ε, ρ, τ)`，规范键为 `k(z) = (u, σ, β, ε)`，支持作用域局部推理。
    2. **冲突感知更新规则（Conflict-Aware Update Rules）**：定义四种更新策略：
        - **可信度调和（Credibility reconciliation）**：对描述同一事实的不兼容主张，基于证据强度决定胜负，胜者标记 CONFIRMED，败者保留为 SUPERSEDED 或 CONTESTED。
        - **协调处理（Coordination handling）**：对依赖循环或资源冲突，保留候选条目并附加冲突信号，重新规划而非删除。
        - **槽位优先状态合并（Slot-first state merge）**：对相同键但值不同的声明，基于证据分数、时效性和 LLM 平局决断决定当前状态。
        - **证据累积（Evidence accumulation）**：相同键和值重复出现时，合并来源、时间戳和证据，而非产生重复条目。
    3. **渲染视图（Rendered Memory）**：将最终内存外部化，包含当前状态、争议项、转换日志，供下游智能体使用。软件状态任务中，渲染器在预算受限时对紧密耦合槽位进行分组。
- **算法流程（文字描述）**：输入当前内存和更新 → 提取结构化条目 → 对条目分类处理（智能体发现直接附加；软件状态声明按键路由并比较） → 运行符号检查（依赖循环、资源冲突） → 分类冲突（可信度/协调） → 仅对未解决的语义情况调用 LLM 调和器 → 渲染内存文档。
- **证据加权打分**：软件状态解决器使用的分数为 `s(z) = w(evidence-type) + 40·1[git_commit ≠ ∅]`，代码变更/事件热修复权重最高（60），过时观测权重最低（4）。仅在证据强度打平时才使用时效性，最后才回退到 LLM 评判。

## 七、优点

- **问题定位新颖**：将矛盾处理重新定义为“内存更新”而非“答案聚合”，填补了现有智能体记忆系统中“冲突状态”作为一等属性的空白。
- **架构设计务实**：用廉价符号检查处理机制性冲突，仅在语义未决时调用 LLM，平衡了效率与效果。
- **统计严谨性**：主结果使用配对 McNemar 检验（p<10⁻⁶），消融实验提供 bootstrap 置信区间和 p 值，降低了随机波动的解释风险。
- **公平性意识**：标签盲协议消除了“权威来源”名称作为外在提示的混杂因素；同池基线平价设计使比较聚焦于内存更新而非提示丰富度。
- **可复现承诺**：每个运行器记录逐样本结果，可根据已完成的运行离线重新计算结果，而无需重新查询托管模型；单元测试覆盖核心组件。

## 八、不足与局限

- **应用局限**：LatticeMind 不是搜索或深思熟虑的通用替代品；在 TravelPlanner 上出现性能回退（-7 点），对需要全局迭代优化的任务帮助有限。
- **协调冲突仅设计级**：协调处理作为保守安全覆盖存在，作者明确声明“不作为经验验证的改进目标”，缺乏实证支持。
