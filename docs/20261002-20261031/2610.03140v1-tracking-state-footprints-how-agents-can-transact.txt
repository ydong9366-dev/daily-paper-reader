## ABSTRACT 

Can AI agents transact? We argue that they must: as multi-agent sys-tems (MASs) increasingly write code, deploy infrastructure, modify databases, and call web services, lost updates or stale reads can be catastrophic. Although MASs increasingly execute plans in parallel, current orchestrators do not track the state that agents read and write. As a result, concurrency anomalies manifest even in simple coding tasks. We frame MAS coordination as a data management problem and propose to describe agents by their state footprint : the state they read and write across their own local context and state, as well as the state of the orchestrator and external systems. We posit that MASs require guarantees similar to those of databases, but providing them raises new challenges and opportunities: unlike database transactions, agents do not read from a fixed schema or an isolated snapshot, and cannot be replayed deterministically upon failure. They can, however, resolve conflicts semantically instead of aborting, enabling new forms of concurrency control and conflict resolution. Towards agents that can transact, we outline a vision for next-generation agent orchestrators and transactional interfaces for external systems to participate in agentic transactions.

## 1 INTRODUCTION 

Recent advances in LLM agents enable collaborative multi-agent systems (MASs) to solve complex tasks, including bug fixing [12, 15, 45], deployment & incident management [32, 38], or supply chain control [32, 60]. In a typical MAS, a planner agent decom-poses a user’s goal into subtasks, and an orchestrator dispatches them to specialized worker agents, often in parallel to finish faster. The workers read and modify shared state along the way: a code repository, a database, or a third-party service. Yet, MASs remain unreliable in practice [51, 55]. The usual explanation lies in the mod-els: LLM agents are nondeterministic, prone to hallucinations that cascade into downstream agents [16, 27, 45, 48] or trigger endless thought loops [28]. In this paper, we argue that this unreliability lies not only in the models, but also in how their work is coordinated.

Consider a team of coding agents refactoring a codebase. A plan-ner splits the work into subtasks: one agent changes a core com-ponent, others update the code that uses it. Every agent completes its subtask successfully, yet the merged code fails its tests: some agents updated callers against the old version of the component, and two concurrent agents edited the same file, one silently over-writing the other. A better LLM would not have prevented either failure, since each agent acted correctly in isolation. The issue is that most of today’s orchestrators track control flow , i.e., which task runs after which, but not data flow , i.e., which state each task reads and writes [15, 27]. The ML community has greatly improved planning [19, 28, 52], collaboration [57, 62], speed, context capacity, and token costs, but these advances govern what agents decide, not how their access to state is coordinated. The data management community, in contrast, has long-established paradigms for concur-rency, fault tolerance, and consistency [3, 8, 59], yet these are not systematically applied to agentic orchestration. In this paper, we examine MAS coordination through a data management lens. Our central thesis is that reliability must come from the orches-trator, not the models alone: plans and actions come from LLMs and may be wrong, but the guarantees must come from a deterministic component. This component should record agents’ state accesses and enforce ordering regardless of how the model behaves. State is scattered across three scopes: the agent’s own context and local files, the orchestrator’s plan and task status, and external systems (code repositories, databases, web services). In this paper, we de-scribe a task by its footprint 1: the state it reads and writes across all three scopes. We outline how footprints underpin the guarantees that databases provide: atomicity, consistency, isolation, durability. Multi-agent orchestration presents new challenges. Unlike a database transaction, an agent does not read from a fixed schema but from whatever enters its context window. In addition, its execu-tion cannot be replayed deterministically in case of failure. At the same time, agents bring a capability that transactions lack: instead of aborting on a conflict, they can inspect it and perform seman-tic conflict resolution. MASs bear similarities to databases in the 

guarantees they need, but not in the mechanisms that provide them. This paper makes the following contributions: 

• We show that MAS coordination failures can stem from un-tracked data dependencies: orchestrators order tasks, but not the state they read and write (§3). We characterize anomalies on four coding tasks (§4). 

• We identify three scopes of state in MASs (agent-local, orches-trator, and external) that differ in who can observe, revert, and reproduce them in case of conflict or failure (§5). 

• We propose to track agentic tasks by their footprints : the state they read and write across all scopes, capturing conflicts that span scopes and may emerge dynamically during execution (§5).

## 2 A BRIEF INTRODUCTION TO MAS 

Architecture. Within a single agent (Figure 1), execution proceeds via a closed loop between the LLM and runtime harness. The LLM is responsible for reasoning, decision-making, tool selection, and output evaluation. As LLMs operate strictly on text, they rely on a 

harness , a wrapper around the LLM(s), that manages state, invokes tools, and executes code [14, 56]. The harness parses the output of an LLM, looking for special tags that LLMs are trained to produce in their output [35]. The harness invokes the requested tools and routes their results back to the LLM. An MAS coordinates an ensemble of such agents to solve a user-specified task. In an MAS, individual LLM agents assume dedicated roles (e.g., coding, testing, deploying) [24, 27, 45]. To orchestrate execution, a dedicated planner decomposes the high-level goal into structured subtasks with constraints [9, 20, 52, 62]. Plans manage a speed vs. correctness tradeoff and may be dynamically modified on the fly. The literature mainly distinguishes sequential and DAG-based topologies. A sequential plan executes subtasks strictly one by one. While safest to coordinate, sequential plans are also the slowest [45]. DAG-based topologies use scatter-gather patterns to run subtasks in parallel, merging the artifacts at the end [27]. 

Historical evolution. Following AutoGPT [21], early MAS frame-works (2023–24) such as ChatDev [45] and LangChain [13] executed static plans with rigid coordination [20]: an intermediate failure re-quired a complete restart [28]. State management and idempotency were left to the user. Second-generation runtimes (2024–26) such as LangGraph [34], MetaGPT [27], AutoGen [54], and ChatDev 2.0 [15] introduced DAG-based execution with dynamic replan-ning [28], task verification, and self-healing. They can detect and resolve many failures without human intervention [7, 20, 57, 58], but without guarantees about the state their tasks share. Emerging

## 3 MULTI-AGENT COORDINATION AS A DATA MANAGEMENT PROBLEM 

MAS coordination is fundamentally a data management challenge: coordination correctness depends not only on control-flow (task ordering and temporal scheduling) but also on the data-flow : data dependencies [47], output visibility and isolation [1, 2, 26] across agents. Agent orchestrators so far primarily capture control flow [15, 27, 34], neglecting data dependencies arising from conflicting reads and writes to shared state. Agents may thus act on a stale or incon-sistent view of the state, causing failures that control-flow ordering alone cannot prevent. We illustrate the coordination problems on a seemingly simple agentic coding example, which shows that coor-dination and isolation schemes arise well beyond databases.

Read-After-Write (RAW) violation. T2 correctly executes after T0 terminates, inheriting the updated constructor signature. How-ever, control-flow ordering only guarantees that T0 has finished, not that its side effects are semantically compatible with down-stream tasks. T0’s removal of the stored providing_args is one such side effect. T2’s debug path expects this field, but because this data dependency is unrepresented in the graph, the conflict bypasses ordering checks and surfaces only when post-merge tests execute the missing path. A RAW violation is similar to a stale read 

in classical concurrency control, except that this data dependency is never expressed in a way for the workflow to catch. While WAW and RAW violations resemble those in traditional databases, where dependency problems are typically resolved by ordering, the violations in MAS require mechanisms beyond task ordering . In the RAW example, T2 ran after T0, yet the failure occurred regardless. The cause was not when T2 ran, but whether T0’s write was checked against a dependency. Similarly, fixing WAW requires not simply ordering tasks but dependency tracking and a merge strategy to reconcile two concurrent writes.

## 5 THE THOUSAND FACES OF AGENTIC STATE 

The anomalies of Section 4 arise because the state that agents read and write is scattered across components with very different proper-ties. We distinguish three scopes of state: agent-local, orchestrator, and external (Table 2). They differ along three axes that determine how conflicts can be detected and repaired: who can observe the state, whether it can be reverted , and whether it can be reproduced 

after a failure. We describe each scope through Example 3.1. 

Agent-local state is private to a single agent: its context, which mutates on every iteration of the agent loop, the status of its tool calls, and, depending on the deployment, a private filesystem or key-value store. Only the agent observes this state, and its most valuable part, the context, cannot be reproduced: it is the product of prior LLM generations rather than a deterministic function of the inputs. Suppose T2 crashes while updating contrib/auth , after reasoning through several candidate edits but before writing any. The repository is unaffected, but nothing records what T2 had already decided or partially produced, and its local filesystem may be left dirty. A restarted agent must either redo the reasoning or infer its predecessor’s progress from the partial changes left behind. 

Orchestrator state comprises the cross-task runtime context main-tained by the orchestrator: execution plans, task and data depen-dency graphs, task status, and completion signals. As the owner, the

orchestrator can observe, log, and revert it at will. Some systems additionally expose a shared blackboard that all agents read and write; since the orchestrator mediates every access, conflicts on it could, in principle, be detected. Recent work begins to bring concur-rency control to MAS workflows [37, 40], but to our knowledge, no orchestrator tracks conflicts over state that spans all three scopes. 

External state resides outside the direct control of the orchestrator and the agents, e.g., repositories, databases, and third-party APIs. It is shared with other agents and outside consumers, and it persists after the workflow completes. A task that triggers a deployment through a third-party API produces an effect that is visible imme-diately, possibly to other consumers before any later task flags a conflict. Undoing it requires a compensating action, as in the saga pattern [22]; retrying it is safe only if the operation is idempotent. In both cases, external writes must be tracked for conflict detection. 

Agent state footprints. The three scopes suggest an underlying model. Each task operates with a read set and a write set comprising items from any scope: a repository file, the agent’s context itself, a blackboard entry, or a tool call result. Together, they form the task’s state footprint . Two tasks conflict if one writes an item that the other reads or writes, and a schedule is conflict-ordered if every pair of conflicting tasks is ordered. Tracking an agent’s footprint is hard because the read and write sets are not fixed a priori. An agent’s read/write set is materialized in its context window, and new dependencies may emerge during execution. A sound approxi-mation is to record everything an agent observes through its tool calls and task inputs. Interestingly, one can treat agent searches like predicate reads. Since agents can perform semantic recovery 

rather than rolling back to the state before a failed or conflicting task, an agent may be able to self-heal from a half-written file or a conflicting state mutation. But the orchestrator needs to have a complete picture of what state has been mutated, and this can be provided by our proposed state footprints. 

## 6 VISION AND RESEARCH CHALLENGES 

Making MAS reliable requires rethinking how transactional data-base guarantees meet the unique challenges of MAS. Existing work addresses individual pieces: isolation [37, 40], fault tolerance [7], and replanning [31], but none treat state management holistically across all three considered scopes. We argue that next-generation orchestrators should generalize: the state footprint of each task is de-clared or inferred (§5), and the orchestrator records the provenance linking each write to the tasks that consumed it. This separates nondeterministic LLM behavior from deterministic guarantees: the plan and task actions come from LLMs, which sample outputs and may be wrong, but the guarantees come from a deterministic or-chestrator that records footprints and enforces ordering regardless of LLM behavior. We outline this vision via well-established ACID concepts and identify open research questions.

## 6.1 Atomicity and Reversibility 

A database transaction’s writes target a single storage engine that can undo them. In contrast, an agent task may edit files in a local checkout, insert into a database, update configuration files, and call a web service, each with its own notion of versions, if any. Reverting any of these systems in isolation is well understood, e.g., git, filesystem sandboxes, ZFS snapshots, etc. But reverting a task 

requires these heterogeneous systems to roll back together, to states corresponding to the same logical point . Coordinated rollback has been studied for relational databases, sagas [22], durable workflows [4, 49], and cloud applications [44], but not across a mix of these systems touched by a single agent. Parallelism compounds the problem: when concurrent agents write to shared (external) state, aborting one agent must not undo the effects of another. 

Our vision. Every task execution should carry a transaction iden-tifier that propagates to every system it touches: the harness, the orchestrator, and each tool. Tool calls are recorded against this iden-tifier together with the task’s footprint (§5), so that the orchestrator can abort a task by reverting every write: through a snapshot where the system supports versions, and through a compensation action where it does not. Because agents spawn sub-agents, identifiers must nest, so that a sub-task can be aborted without aborting its parent. Footprints also scope aborts under parallelism: only the aborted task’s writes, and the tasks that read them, are undone, while concurrent tasks with disjoint footprints proceed. 

Open research questions. (i) How can filesystems, databases, version control, and web services agree on versioning conventions so that one transaction identifier maps to a consistent snapshot in each? (ii) What is the right abort granularity for long-running agent tasks: the whole task, individual tool calls, or reasoning steps in between? (iii) When should an orchestrator roll back, and when should it let an agent repair its partial effects via semantic recovery? 

## 6.2 Consistency and Isolation 

Agents’ concurrent access to shared state may cause their actions to interfere, giving rise to concurrency anomalies such as lost updates, inconsistent reads, or writes that lead to an incorrect state. The ACID notion of consistency [23] requires that a transaction never leaves the database in violation of its integrity constraints; a seem-ingly simple invariant, but very hard to get right in databases. The agentic analogue is that an orchestration must preserve the task’s invariants . Those invariants, however, vary per task. In a coding task, a trivial invariant could be that the repository must compile and pass its tests. Orchestrator state poses little difficulty here: the orchestrator owns plans, dependency graphs, and task status, and can check their invariants directly. External state is different; its invariants are implicit and checked late (e.g., at git push ). In Ex-ample 3.1, T0’s removal of providing_args broke the invariant that every referenced attribute exists, yet the only check was a test suite at commit. That violation was caught because it failed loudly. However, the T1 and T2 fixture collision passed silently and could contaminate the remote repository. While the orchestrator state remained consistent throughout, the repository did not. Isolation governs when a transaction’s effects become visible to others. For external state, the answer differs by resource: a local checkout can hold writes from the remote repository but not from co-located tasks, whereas a third-party service exposes an effect immediately. Agentic isolation (in the database sense rather than sandboxing for security) also extends beyond data, e.g., acquiring a lock before triggering a deployment. The core difficulty, however, is that a task’s state footprint is unknown a priori: it spans scopes and emerges only during execution. Consider a write skew : a refactor-ing agent sees no references to providing_args and removes its definition, while a concurrent debugging agent sees the definition and adds a reference. They edit different files and merge without a textual conflict, yet violate the invariant that every reference re-solves. A strong guarantee is serializability [42], where tasks appear to execute atomically. However, this does not fit MASs, involving long-running, nested computations. 

Our vision. Orchestrators should take responsibility for concur-rency control [11]: agents declare, or the orchestrator infers, tasks’ state footprints, and the orchestrator detects schedules that are not conflict-ordered before their effects are published. Isolation should then be defined per resource class, stating when a task’s effects become observable to tasks sharing local state and to outside observers. A detected conflict must invalidate both the conflicting writes and every decision derived from them 2. Rolling back is not the only remedy: with invariant-guided semantic recovery , agents revise invalidated decisions and repair conflicting effects, with ap-plication invariants serving as the acceptance criterion for the resulting state [33]. We envision novel hierarchies of agent-centric consistency [50] and isolation levels [2] tailored to MAS. 

Open research questions. (i) How can invariants over internal and external state be specified, or inferred from user intent? (ii) At what granularity should observed reads be tracked (files, functions, or API contracts) to avoid false conflicts that needlessly limit parallelism? (iii) What agent-centric consistency and isolation levels can we devise to navigate performance-accuracy trade-offs? 

## 6.3 Durability and Fault Tolerance 

In MASs, “committed” (i.e., durable) requires a commit that spans many systems with different guarantees: a git push, a database write, a third-party API call. The orchestrator can only acknowledge a task as complete once each system acknowledges its part. Acknowl-edgments must be surfaced hierarchically, from external systems to tools, through the agent harness and all the way to the orchestrator. Upon failure, the standard remedy for recovery, replaying a failed task, assumes deterministic and idempotent execution. LLM agents offer neither: re-running a task samples a different output, and its tool calls may repeat external side effects. What can be recovered, and how, depends on the state scope (Table 2): versioned external state can be restored from a snapshot [10], unversioned effects re-quire compensation [22], derived artifacts can be recomputed, and agent context can only be regenerated by re-prompting. 

Our vision. The provenance recorded alongside footprints should become part of a recovery log. On failure, the orchestrator discards only the state, causally downstream of the failed write, restores it per scope, and maintains a ledger of compensations for effects it cannot roll back. To make replay deterministic, the orchestrator should further log every LLM output and tool response of a task, as durable execution engines log activity results in their event history [49]. A replayed task consumes the logged results up to the point of failure instead of resampling them. External systems, in turn, must acknowledge when an effect has become durable and visible, not merely that a request was accepted. Instead of replaying a failed agent from scratch, the orchestrator can hand the recorded footprint and partial effects to a fresh agent, in order to attempt semantic recovery. Importantly, under paral-lelism, tasks whose footprints are not dependent on the failed task’s footprint can continue unaffected. 

Open research questions. (i) What constitutes an agent’s foot-print checkpoint: can we checkpoint its context at an intermediate reasoning step, so that recovery need not restart the task? (ii) How can we extend existing recovery mechanisms to deal with heavy non-determinism? (iii) How can durability acknowledgments from heterogeneous systems compose into a single, trustworthy commit? 

## 6.4 Reuse and Dynamic Replanning 

Agents run loops: they try out branches of computation, evaluate their own progress, and revise their plans as they discover new information. Traditional systems would restart a failed task from scratch, discarding many iterations of costly reasoning. Unless the verified work of a failed run can be salvaged, a rerun re-executes ev-ery task, including those whose results were unaffected by missing dependencies. Reuse, however, requires knowing which intermedi-ate results remain valid. A result that was checkpointed before an agent discovered a new data source, for instance, may no longer be valid, while a result whose inputs have not changed is safe to keep. 

Our vision. Footprints and provenance turn reuse into a valid-ity check. A task’s result remains valid if no item in its read set changed since the result was produced, much as incremental view maintenance decides which views to refresh. Replanning then be-comes a “diff” between the old and new plan rather than a restart. Within long-running loops, nested checkpoints in the style of Na-iad’s timestamps [41] allow an agent to resume from its last valid iteration instead of from the start. Under parallelism, a newly added dependency serializes only the conflicting tasks, so the rest of the plan keeps running concurrently. 

Open research questions. (i) When is a checkpointed agent result reusable, given that a fresh run would sample different inputs and produce a different chain of thought? (ii) Can we build cost models to predict the trade-off between checkpointing cost and task replay? (iii) How should checkpoints be taken in nested agent loops so that recovery resumes mid-loop without persisting every iteration? 

## 6.5 Agent-Ready External Systems 

The mechanisms above assume that external systems cooperate, yet most were built for human-paced clients whose requests are infrequent, deliberate, and mostly correct. Agents invert this as-sumption: they explore through speculation [36], issue many re-quests in parallel, and many of their effects will later be aborted, retried, or compensated. An agent that mistakenly provisions vir-tual machines or triggers a payment leaves the orchestrator with no means of undoing the effect beyond an idempotency id and a compensation. We therefore argue that external stateful systems must be redesigned for abort-heavy, stateful workloads. 

Our vision. We envision five primitives. First, external systems accept a form of transaction identifier of a task, propagate it to downstream calls, and can revert all associated effects. Second, writes are either (i) tentative by default and take effect only upon confirmation, following the try-confirm-cancel (TCC) pattern [25, 43] or (ii) compensable [22]. Third, writes can be conditioned on the state that their task reads, similarly to predicated single-shot transactions [29]. Fourth, every operation declares whether it is read-only, idempotent, or reversible, together with its inverse. Tool annotations of MCP [39] are already an early step in this direction. Fifth, and most importantly, external systems offer cheap state versioning/branching, so that parallel agents can each speculate on a private copy [36] and merge through a step that surfaces conflicts. 

Open research questions. (i) Can we create protocols that carry transaction identifiers, read preconditions, visibility contracts, and share read/write sets across arbitrary agents and services? (ii) Agen-tic transactions run for minutes or hours; how should systems bound this retention, e.g., by expiring tentative writes into au-tomatic cancellations, without aborting legitimate long-running work? (iii) Are novel compensation “contracts”, apart from SAGAs and TCC, needed in order to support emerging agentic workloads? 

## 7 THE ROAD AHEAD 

The four guarantees we used here are not orthogonal: they rest on the same substrate, namely state footprints and the provenance that links each write to the tasks that read it. Atomicity uses write sets to determine what to undo. Isolation uses read and write sets to detect conflicts. Recovery uses provenance to discard only causally dependent downstream state. Reuse uses read sets to decide which results remain valid. What differs across scopes is only the guaran-tee enforcement mechanism, and in external state that mechanism must be exposed by the systems themselves. An orchestrator that records footprints can provide all four guarantees, and relax each independently where parallelism matters more than strictness. We focused on coding agents as the most mature agentic use case, and because git provides a natural transactional substrate: staging, atomic commits, and cheap rollback. Most domains lack such a sub-strate. Supply-chain operations, scheduling, and incident response operate without version control; effects are immediately visible and often irreversible. Human-in-the-loop checkpoints offer a safeguard today, but time-critical tasks demand autonomous execution. These domains need guarantees even more than coding does, and they depend most on external systems becoming agent-ready. One may argue that better models can make these concerns ob-solete. We argue for the opposite: stronger models will be trusted with longer tasks, more parallel agents, and more consequential side effects, which enlarges exactly the state that must be coordi-nated. Coordination, isolation, and recovery are properties of the system, not of the model. The data management community has spent decades of researching methods and abstractions. Agentic orchestration is where they are needed next.
