# OpenDGO: Benchmarking Multi-Agent Organizations Across Diverse Application Domains 

# Xunkai Li*, Miao Zhang*, Zekai Chen*, Xuaner Chen, Yu liu, Rui Qian, Xun Wu, Hongchao Qin, Rong-Hua Li 

## Abstract 

Large language model (LLM)-based multi-agent systems are in-creasingly applied across diverse domains, yet different applica-tions require different forms of agent organization. Existing studies typically adopt predefined organizations, such as Star, Chain, and Tree, or learn communication graphs to improve performance on specific tasks. However, these methods are largely designed and evaluated within a limited set of application domains, providing little understanding of whether an organization effective in one domain remains suitable for others with different collaboration requirements. We present OpenDGO , a controlled benchmark and analysis framework covering six real-world domains and three collaboration settings: Sequential Dependency, Parallel Decompo-sition, and Information Integration. Under matched tasks, agents, tools, and resource limits, OpenDGO compares fixed and learned organizations while separately examining communication graphs, role assignments, input assignments, resource budgets, and compo-nent failures. Our results show that there is no “one-organization-for-all” solution: preferred organizations vary across applications, and even the same communication graph can yield different out-comes under different role and input assignments. These findings highlight the need for application-dependent organization design, aiming to understand which organization is suitable for a given application, under what conditions, and why .

## 1 Introduction 

Large language model (LLM)-based multi-agent systems (MASs) are increasingly used in web-centric applications, such as web search, online recommendation, and document question answering, by coordinating multiple specialized agents to solve complex prob-lems [13, 14, 18]. A basic design choice is how these agents should be organized, including which agents can communicate with each other and which role each agent plays in the communication graph

(e.g., which agent is responsible for a specific function, such as implementation, testing, or verification). Common choices include centralized Star structures, ordered Chain structures, hierarchical Trees, and irregular graphs learned automatically for a given task. Different application domains naturally favor different forms of organization. In Coding, issue analysis, implementation, and testing form an ordered workflow, making Chain- or Tree-like organiza-tions intuitive choices for passing intermediate results between stages. Finance similarly requires extracted numbers to move re-liably through calculation and verification. Legal and Scientific Research instead require several agents to examine different doc-uments, rules, or claims before their conclusions are combined, which can benefit from more distributed communication. Recom-mendation often allows user history, reviews, and item attributes to be analyzed in parallel before aggregation, making highly central-ized sequential communication less necessary. These application domains therefore place different demands on the organization of an agent team, making a single organization unlikely to work equally well across all of them. The central question is thus which type of multi-agent organization is appropriate for a given application domain, and why .Existing studies have mainly focused on evaluating which orga-nizations perform well within a specific application domain, while paying little attention to whether the same organizations remain effective in other domains with different collaboration require-ments [1, 10, 15]. For general-purpose MASs, this distinction mat-ters: an organization suited to the sequential workflow of Coding may not work equally well for Legal analysis or Recommendation, where agents need to collaborate differently. Furthermore, the com-munication graph is not the only factor affecting performance. Even within a fixed Tree, placing a verifier at the center rather than at a peripheral node changes how it communicates with other agents. Similarly, assigning different inputs, such as code files or financial tables, to different agents can affect their collaboration. To examine these factors, we evaluate the same organizations across diverse domains, keeping the source task, agent model, tools, and resource limits fixed within each comparison while separately varying the communication graph, role assignment, and input assignment. This allows us to assess how organization preferences change across domains and identify the factors behind these differences. Our motivating observations in Fig.1 support this view. Organiza-tion rankings vary considerably across domains and collaboration settings, and neither fixed nor learned organizations consistently dominate all conditions. The same communication graph can also produce different results when role assignment or input assignment changes. For example, under a fixed Tree graph, assigning a key role to a central node can be preferable in some settings, while assigning it to a bridge node becomes more effective in others. shape alone, but by how the communication graph, role assignment, and input assignment jointly match the collaboration required by the application. Motivated by these findings, we present OpenDGO , a con-trolled benchmark and analysis framework for multi-agent organi-zation. OpenDGO covers six application domains—Coding, Finance, Biomedical, Legal, Scientific Research, and Recommendation—and summarizes their collaboration requirements through three repre-sentative settings: Sequential Dependency , Parallel Decomposition ,and Information Integration . Under matched source tasks, agents, tools, and resource limits, OpenDGO compares six fixed organiza-tions with recent learned organization methods. It further varies the communication graph, role assignment, input assignment, resource budget, and component failures separately, allowing the effect of each factor to be examined under the same evaluation setting. We also relate organization performance to graph properties and ac-tual communication traces to explain why different organizations behave differently across applications. OpenDGO therefore aims to answer a concrete question: for a given application and collaboration requirement, which organization should be used, under what resource conditions, and why? 

Our Contributions. (1) Comprehensive Benchmark. We introduce OpenDGO, a controlled benchmark spanning six real-world do-mains, three collaboration settings, six fixed organizations, and recent learned organization methods, enabling organization evalu-ation across heterogeneous applications rather than within a single domain. (2) Controlled Analysis. We separately examine communi-cation graph, role assignment, input assignment, resource budget, and failures, and connect these factors with graph properties and communication traces to explain their effects. (3) Valuable Insights. 

We show that no organization serves as a one-for-all solution: pre-ferred organizations vary across applications, the same commu-nication graph can behave differently under different role and in-put assignments, and practical choices involve clear quality–cost– robustness trade-offs.

## 2.2 Related Work 

Recent benchmarks have begun to evaluate how LLM agents col-laborate rather than only whether they complete tasks. MultiA-gentBench compares representative communication structures, in-cluding Star, Chain, and Tree [18], while AgentsNet examines coor-dination across different network structures and agent scales [6]. More recent benchmarks investigate distributed coordination (SILO-BENCH), Web-agent collaboration (AgentWebBench), and collabo-ration under partial observability (MASBench) [4, 16, 17]. However, these benchmarks mainly focus on specific environments or col-laboration mechanisms, providing limited understanding of how organization preferences change across heterogeneous application domains and different role and input assignments. OpenDGO ad-dresses this gap through controlled cross-domain comparisons to understand which organizations are effective under different appli-cation conditions and why. 

## 3 Motivating Observations 

Existing studies provide limited understanding of whether the same organization works across different application domains and how role and input assignments affect its performance. We examine these questions through two controlled analyses, as shown in Fig. 1. 

Observation 1: Organization preference varies across ap-plications. As shown in Fig. 1a, GoAgent and ARG-Designer win 12 of 18 domain–task conditions, while fixed organizations retain five wins. Among fixed organizations, Tree achieves the highest average quality on Sequential Dependency (62.6%), whereas Com-munity leads on Parallel Decomposition (67.0%) and Information Integration (66.9%). These results show that no organization con-sistently dominates across applications with different collaboration requirements. 

Observation 2: Communication graph alone is insufficient. 

We fix the six-agent Tree and vary role and input assignments. As shown in Fig. 1b–1d, Sequential tasks favor Center + Centralized (67.7%), dropping to 60.2% when the key role moves to Edge. Parallel Decomposition and Information Integration instead favor Bridge + Distributed (54.5% and 58.7%). ## 4 Organization Design and Analysis 

OpenDGO aims to understand when a multi-agent organization is effective and why. We separate the collaboration required by a task from the organization used to support it, and relate controlled orga-nization changes to communication behavior and task performance. Fig. 2 summarizes the overall framework. 

## 4.1 Task Construction 

Source Tasks. OpenDGO covers six domains: Coding, Finance, Biomedical, Legal, Scientific Research, and Recommendation. For each source instance, we preserve its original question, answer target, task inputs, and evaluator, while dividing the required work among six domain-specific roles with corresponding input assign-ments. 

Collaboration Structures. Each task is instantiated under three representative settings. Sequential Dependency requires agents to complete dependent steps in order. Parallel Decom-position distributes independent subtasks across agents before combining their outputs. Information Integration requires agents to combine and reconcile information from different sources. These settings specify how agents collaborate without prescribing their communication graph. 

Task Dependencies. We represent the required collaboration as a task dependency graph 𝐻 𝑥,𝑠 , whose vertices denote agent outputs and edges represent their dependencies. It specifies which outputs are needed by subsequent agents without determining how those agents communicate, allowing the same task requirements to be evaluated under different organizations. 

## 4.2 Controlled Organization Design 

Organization Space. Following Sec. 2.1, an organization 

O = (𝐺, 𝑅, 𝑃, 𝐼, 𝐵 ) specifies the communication graph, agent roles, role assignment, input assignment, and execution budget. We consider six fixed organizations—Star, Chain, Tree, Ring, Mesh, and Community—together with three learned methods: G-Designer, ARG-Designer, and GoAgent. A Single-Agent setting with access to all task inputs serves as the reference. 

Controlled Interventions. OpenDGO examines organizational factors under matched source tasks, agent models, tools, and evalu-ation protocols. Varying 𝐺 compares communication graphs, while fixing 𝐺 and changing 𝑃 or 𝐼 isolates the effects of role and in-put assignments. We further examine graph properties through matched graph variants and evaluate different resource budgets and component failures. Other conditions are held fixed within each comparison. 

Execution Traces. Agents exchange messages only through permitted edges, and a designated agent produces the final answer from the inputs and messages available to it. Each execution records communication paths, intermediate outputs, message rounds, and token usage, allowing us to examine how different organizations operate.

## 4.4 Evaluation Protocol 

Task Quality. Each domain retains its original evaluation metrics, including resolve rate, exact match or accuracy, claim-verification accuracy, and Hit@1 where appropriate. 

Coordination Behavior. Input coverage and propagation la-tency measure information delivery; duplicate-message rate and aggregation load capture communication overhead; conflict reso-lution and cross-group communication characterize collaboration between agents. 

Cost and Reliability. Token usage, message volume, and execution time measure organization cost. Controlled agent and communication-link failures evaluate the ability of different organizations to maintain performance under disruptions. 

## 5 Experiments and Analyses 

We examine how organization choice depends on task demands, input placement, and deployment constraints through four ques-tions. Q1: How do single-agent, fixed, and learned organizations compare across domains and task structures? Q2: How do role placement and information allocation affect a fixed topology? Q3: 

Which structural properties distinguish useful organizations for different tasks? Q4: How does organization choice change with token budgets, component failures, and unreliable inputs? These analyses progress from comparative effectiveness to organizational factors, structural explanation, and deployment trade-offs. 

## 5.1 Experimental Setup 

Datasets and evaluation. We cover Coding with SWE-bench Ver-ified [3, 9], Finance with FinQA [2], Biomedical with BioASQ Task B [11], Legal with LegalBench [7], Scientific Research with Sci-Fact [12], and Recommendation with Amazon Reviews 2023 [8]. The domain-specific scores include resolve rate, exact match or ac-curacy, claim-verification accuracy, and Hit@1. Each domain covers Sequential Dependency, Parallel Decomposition, and Information Integration. 

Methods and comparison protocol. We compare Single Agent; six fixed organizations (Star, Chain, Tree, Ring, Mesh, and Commu-nity); and G-Designer [15], ARG-Designer [10], and GoAgent [1]. The single agent receives the complete set of task inputs available collectively to the six-agent systems. The target protocol pairs 500 tasks per domain–structure cell across methods, with the same model, tools, budget, stopping rule, scorer, and five seeds. ## 5.2 Organization Effectiveness (Q1) 

To address Q1 , we evaluate ten methods across six domains and three collaboration settings, and further examine whether organi-zation preferences transfer across LLM backbones. 

Overall Performance. ## 6 Conclusion and Future Directions 

In this work, we present OpenDGO to systematically study how LLM-based multi-agent systems should be organized. Across six real-world domains and three representative collaboration settings, we compare fixed and learned organizations and further examine role placement, information allocation, graph structure, resource budgets, and component failures. Our results show that organi-zation effectiveness is strongly conditioned on the collaboration required by the task: no single topology consistently dominates, and the same graph can behave differently when roles or informa-tion are rearranged. Based on these findings, we highlight several directions for future multi-agent organization research. 

Task-Conditioned Organization. Our results suggest that searching for a universally strong communication topology is unlikely to be sufficient. Sequential Dependency, Parallel Decomposition, and Information Integration tasks impose different information-flow requirements and therefore favor different structural properties. Future systems should infer collaboration demand from the task and adapt their organization accordingly, rather than applying the same topology to every instance. 

Organization Beyond Topology. Communication structure alone does not determine team effectiveness. Role placement and information allocation can substantially change the behavior of the same graph, indicating that topology, capability placement, and information distribution should be considered jointly. Future organization designers should therefore move beyond optimizing only 𝐺 toward jointly reasoning over (𝐺, 𝑃, 𝐼 ) and, when necessary, resource constraints 𝐵 .

Behavior-Grounded Organization Design. Static graph sta-tistics provide only an incomplete explanation of multi-agent col-laboration. Our analysis shows that structural properties matter through their effects on information delivery, propagation delay, redundancy, and information integration during execution. Future methods could directly use message-level traces and information-flow signals to design organizations, so that communication struc-tures are optimized for the collaboration they actually induce. 

Resource-Aware Adaptive Organization. Higher connectiv-ity can improve information access and failure tolerance, but it also increases communication and synthesis costs. The preferred organization may therefore change with token budgets, latency requirements, or component availability. A promising direction is dynamic organization, where communication remains sparse OpenDGO: Benchmarking Multi-Agent Organizations Across Diverse Application Domains WWW ’27, May 10–14, 2027, Dublin, Ireland

## A.2 Task Construction and Structural Matching 

Each package records the dataset version, split, instance and source IDs, selection rule, and a hash of frozen model-visible input. Gold answers, hidden tests, and support labels remain evaluator-only. Where redistribution is restricted, IDs, conversion rules, and hashes provide the reconstruction record. Selection and conversion precede held-out scoring. Sequential packages specify ordered intermediate products; Par-allel packages specify independently analyzable views and their integration; Information Integration packages partition complemen-tary units and, where applicable, verified conflicting or distracting units. The imposed dependency graph describes the conversion, not the source dataset’s original purpose. A conflicting view retains a valid answer path. Packages are screened for an automatic target and sufficient information in the union of their views. Difficulty stratum, input length, input-unit count, intermediate decisions, and source category are recorded. Cross-structure comparisons use matched sources where possible; different source compositions are recorded otherwise. Role responsibilities are domain-specific: Coding separates issue analysis, navigation, implementation, testing, regression review, and integration; Finance separates question, table, and text analy-sis, calculation, verification, and integration; Biomedical separates question typing, retrieval, extraction, reasoning, fact checking, and integration. ## B.2 Backbone-Transfer Protocol 

The comparison in Table 2 changes only the execution backbone: task IDs, input inventory, six-node graph, role assignment, infor-mation allocation, synthesizer, tools, communication rounds, and scoring remain fixed. Shared word or character limits for messages and final answers avoid equating different tokenizers; actual token use is recorded separately. Exact checkpoint revisions, decoding and thinking modes, and failure/retry policies must be logged. The best fixed organization is selected separately for each task structure using the unweighted six-domain average. Single Agent and learned designers are excluded from that argmax. Source-backbone choices should be frozen on a development set before target-backbone testing. Target best-graph selection should use a separate selection split where possible; otherwise its test-set argmax is an optimistic oracle reference and must be reported as such. ## B.5 Controlled Graph-property Analysis 

For each six-node organization, density measures communication volume; diameter measures worst-case propagation distance; mean clustering measures local cohesion; Freeman degree centraliza-tion measures hub dependence; normalized edge connectivity mea-sures disconnection resistance; normalized independent-cycle re-dundancy measures alternative routing; and greedy modularity measures subgroup separation. Graph statistics cannot generally be varied independently. We therefore build matched connected six-node variants that alter one focal property while minimizing changes in the others. The same six focal properties—diameter, edge connectivity, density, modularity, clustering, and cycle redundancy—are to be evaluated under every task structure. Within each task, a separate standardized partial-effect model will be fitted for each property, adjusting for residual changes in other graph properties and domain fixed effects while agents, roles, input allocation, inputs, and budget remain fixed. For a connected six-node graph with 𝑚 edges, density is 𝑚 /15 and normalized cycle redundancy is (𝑚 − 5)/ 10, so redundancy equals 1 .5 density − 0.5. Separate focal-property models must omit this collinear counterpart from their controls; the two coefficients cannot be interpreted as independently identified effects of adding edges. Constant or singular graph controls must likewise be ex-cluded. The message-trace measures below provide diagnostics for the proposed mechanisms.

## B.7 Budget and Fault Protocols 

Token accounting. We count agent inputs, outputs, inter-agent messages, and final aggregation. An organization is Pareto-efficient if no alternative has no greater mean token cost and no lower mean quality, with at least one strict improvement. Common per-task caps range from 6k to 24k tokens and reserve the same final-answer allowance. When collaboration budget is exhausted, later messages are suppressed and the synthesizer uses the state already received. Caps are enforced at message boundaries, so crossing a threshold may enable a complete additional round and need not yield a smooth curve. 

Fault injection. At pressure 𝑝 ∈ { 0, 10 , 20 , 30 , 40 , 50 }%, each trial selects agent or active message-channel failure with equal prob-ability and disables proportion 𝑝 before execution. Failed agents emit no output and failed channels drop messages without retry. Locations vary by seed, so damage depends on whether an integra-tor, articulation point, or redundant component is sampled. Quality is normalized by each topology’s no-failure score to separate re-silience from baseline accuracy.
