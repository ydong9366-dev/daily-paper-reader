Abstract —Designing large language model (LLM) multi-agent systems (MAS) still relies on trial and error and informal “folk wisdom.” Manual studies test only a few communication structures or topologies (e.g., sequential, parallel, shared-memory, or debate), while automated optimizers discard search trajectories after selecting a task-specific workflow. We present a two-phase pipeline for mining reproducible design principles from workflow code and execution traces. We repurpose AFlow’s MCTS optimizer across six composable operators and 26 deterministically verified Enigmata tasks, retaining all intermediate rounds to build a corpus of 28,568 executable workflows. A sandboxed AutoResearch loop then mines orchestration code and prompt templates under an 𝐿 0-penalized validation objective and tests candidate principles on held-out searches. Across 300 feature-mining trials, we identify effects that persist on held-out searches across three levels of workflow design: workflows beginning with independent solvers and one-shot aggregation (Star-first) perform worse (Δ = −0.045 ); persistent shared documents (SharedMemory) outperform debate ( Δ = +0.135 ); and prompt specificity and placeholder-based context routing yield gains comparable to communication-structure selection ( Δ = +0.118 ). More broadly, our pipeline and results show the feasibility of turning discarded search trajectories into a statistical testbed for discovering and validating multi-agent workflow design principles. 

I. Introduction Large Language Model (LLM)–based Multi-Agent Systems (MAS) have become a foundational tool for complex problem solving in many areas such as software engineering [29], economic forecasting [6, 9], and scientific discovery [21, 23]. In these systems, performance depends not only on the base LLM, but critically on the workflow architecture: how agents are connected, how intermediate state is routed, and how role-specific prompts are structured [19]. Yet, designing multi-agent workflows remains largely guided by manual trial-and-error and informal “folk wisdom” (e.g., “more agents improve accuracy” or “multi-agent debate improves reasoning”). This raises the question: Can workflow search traces be used to identify statistically reliable principles for multi-agent system design? 

Recent studies have taken initial steps toward quantifying MAS design choices, examining agent-count scaling [34],

b) Automated Workflow and Prompt Search: Automated search methods have targeted prompt optimization [1, 12, 18], graph connections [31, 36], and agent code evolution [32]. B. Methodological Challenges in Design-Space Mining 

Extracting reliable empirical principles from observational workflow data requires overcoming three operational challenges (summarized in Table II and formalized in Appendix A): 

a) Challenge 1: Design-Space Coverage vs. Implementa-tion Competence: Mining principles requires a sample that both covers many distinct designs and consists of competent 

implementations. The naive route to coverage, generating workflow programs from scratch (e.g., prompting an LLM to write arbitrary orchestration code and prompts without constraints), fails the second requirement: most candidates break with syntax errors or degenerate prompts, burying topological effects under implementation noise. Conversely, keeping only an optimizer’s final argmax workflow 𝑊 ∗ discards the negative and intermediate examples needed to estimate contrasts. We therefore repurpose the MCTS-based AFlow optimizer (§ IV-A) over a structured 6-operator vocabulary O and retain all 𝑁 = 20 intermediate workflows per search under a consistent LLM optimizer policy. 

b) Challenge 2: Domain, Tool, and Grading Confounds: 

On downstream benchmarks such as software engineering or web navigation, accuracy is conflated with domain knowledge, external tool reliability, and LLM-as-a-judge grading noise [19]. IV. Methodology: Sampling and Analysis Phases Our pipeline operates in two stages: a sampling phase 

that pairs full-trace AFlow workflow search (§ IV-A) with deterministic Enigmata evaluation (§ IV-B), followed by an 

analysis phase that mines workflow code and prompt features via a sandboxed AutoResearch loop (§ IV-C). 

A. Sampling Phase: Full-Trace Workflow Search via AFlow 

In AFlow [33], each workflow 𝑊 is represented as an executable Python class in graph.py accompanied by role-specific hard text prompt templates in prompt.py (no soft prompts or gradient updates). Given a task bundle 𝑇 , AFlow searches over workflows across 𝑁 = 20 MCTS rounds: (i) Selection: A parent workflow is sampled from the top-

𝑘 (𝑘 = 4) evaluated workflows using a mixed uniform/softmax distribution ( 𝜆 = 0.2 uniform weight, temperature 𝛼 = 0.4; Eq. 4 in § C-B) to prevent premature collapse; (ii) Expansion: 

An LLM optimizer (fixed to GPT-5.4 at temperature 0) inspects the parent’s code and score history and proposes an edit that adds, removes, or rechains operators in graph.py and refines role prompts in prompt.py (§ D-D); (iii) Evaluation: The child workflow is executed on the 𝑀 = 20 instances in 𝑇 ; and (iv) Backpropagation: Scores and costs are recorded in the search tree. Steps (i)–(iv) are the unmodified AFlow loop; we change three things (§ C-C). First, the operator registry is replaced by our six primitives (Fig. 2), so every proposed edit is a composition of known topologies. Second, evaluation targets fixed Enigmata bundles with deterministic verifiers (§ IV-B). Third, unlike point optimization that returns only 𝑊 ∗, we retain 

all 𝑁 = 20 workflows per trace across 𝐾 = 5 independent runs per condition, capturing both successful and failed designs below the best-so-far envelope (Fig. 4; single tree in Fig. 11, § H). 

a) Composable Operator Primitives and Roles: To span established coordination patterns while permitting multi-stage compositions, we equip the search space with six operator primitives O (Fig. 2, Table VIII; § C-A), synthesized from recent MAS surveys [5, 19, 30, 35]: single-agent linear chaining (Sequential), isolated parallel fan-out followed by one-shot aggregation (Star), blackboard-style sequential writing to a persistent shared document (SharedMemory; 13), all-to-all peer proposal exchange (Debate), and hub-and-spoke or moderated multi-round variants (StarWithCoordinator, DebateWithModerator). An operation in graph.py is an asynchronous call to one operator primitive with optimizer-chosen parameters: 𝑛 ∈ [ 1, 10 ] workers, 𝑟 ∈ [ 1, 5] rounds ,and custom prompts in prompt.py . A round is one complete pass of the operator’s communication pattern, e.g., every SharedMemory worker reads the document once and appends to it, or every Debate worker reads its peers’ proposals once and revises, and an operator with 𝑟 > 1 repeats this pass 𝑟 times, each pass conditioned on the previous one (Fig. 2 is drawn for 

𝑟 =2); these operator rounds are distinct from the 𝑁 =20 MCTS 

search rounds above. Operations can be chained sequentially or conditionally, with the outputs of one operator (and the original problem) forwarded into the prompts of the next (e.g., Star → Sequential in Fig. 3; the most common chains are listed in Table XII). Each operator uses up to two LLM roles (a 

worker and an aggregator/coordinator/moderator ) drawn from 

{GPT-5.4-mini , GPT-5.4-nano }, with at most 20 LLM calls per workflow execution (§ B).

A. Workflow Corpus and Coverage 

Our corpus comprises 28 ,568 executable multi-agent work-flows across 26 Enigmata puzzles (1 ,701 completed AFlow search traces out of 1 ,740 grid cells; Tables IX and XIII, § E), evaluated on 20-instance bundles at $0 .0064 per puzzle instance (∼ $4 ,454 total compute; Table X, § G). Workflows exercise all six operators individually and in chains: Sequential (47 .2%), Star (44 .5%), Debate (22 .3%), SharedMemory (20 .8%), De-bateWithModerator (11 .8%), and StarWithCoordinator (8 .8%; Tables XI–XII).

VI. Discussion and Future Directions 

a) Full-Trace Mining vs. Point Optimization: Automated workflow search and empirical design-space science are com-plementary: the non-argmax rounds that search discards provide exactly the negative and intermediate comparisons needed to explain why designs fail and which edits help. Full traces also expose accuracy-cost trade-offs: SharedMemory costs more than Debate or Star ($0.25 vs. $0.13; Table XI) as the shared document grows, yet its persistent written state avoids the information loss of multi-round dialogue and yields the highest mean accuracy in the corpus. 

b) Beyond Topology-Only Benchmarks: Macro-topology alone ( graph.py ) explains only part of workflow variance (𝑅 2 = 0.521); jointly mining sub-topological prompt structure (prompt.py ) lifts out-of-sample predictive power to 𝑅 2 = 0.638 (§ V-B). Topology benchmarks should therefore report and con-trol for prompt template richness and placeholder routing rather than treating prompts as fixed constants: an ostensibly superior communication graph can be bottlenecked by underspecified role instructions or missing context placeholders. 

c) Operator Evolution and Tool-Rich Domains: Feeding mined regularities back into the operator registry could guide the synthesis of new operator primitives [8, 23] or prune suboptimal entry-point patterns (such as uncoordinated Star-first fan-out) from the optimizer’s search prior, and extending the pipeline to tool-rich domains such as coding [16], games [11], and social simulations [7] will test how topological and prompt principles interact with external tool use and environment feedback. VII. Conclusion We presented an end-to-end pipeline that moves multi-agent LLM workflow design from manual “folk wisdom” toward systematic statistical mining of design principles. Full-trace AFlow search over 26 deterministically verified Enigmata tasks yielded 28 ,568 executable workflows, and a sandboxed, search-level-split AutoResearch loop over 300 trials surfaced out-of-sample verified principles at three granularities: Star-first fan-out degrades accuracy, blackboard-style SharedMemory outperforms conversational debate, and prompt template speci-ficity and placeholder routing matter as much as macroscopic topology. We release the workflow corpus, evaluation harness, and sandboxed analysis pipeline for reproducible empirical research on multi-agent systems. Limitations To isolate multi-agent coordination and prompt structure from external confounds, our experiments focus on tool-free, deterministically verified reasoning tasks from Enigmata and evaluate workflows within a single model family ( GPT-5.4 as the MCTS optimizer and { GPT-5.4-mini , GPT-5.4-nano } as worker and aggregator backbones; § B). While this controlled setup eliminates grading noise and API variance (Appendix A), extending our pipeline to open-weight model families, alterna-tive workflow search algorithms, and tool-interactive domains (such as repository-level coding or web navigation) is a natural direction for future work. Finally, because our corpus harvests trajectories generated along MCTS optimization runs, the mined principles reflect structural regularities within the space of executable workflows explored by the optimizer rather than unconstrained random code generation. B. Analysis Phase 

Each candidate design principle is evaluated per puzzle. For a given feature, workflows are partitioned within each puzzle into a high arm and a low arm : for binary features (e.g., presence of a SharedMemory operator) the high arm consists of workflows where the feature is present and the low arm those where it is absent; for count or continuous features (e.g., mean prompt-template character length) the partition is the per-puzzle median split, with the high arm strictly above the median and the low arm at or below. The per-puzzle effect size is the difference in mean score between the two arms, 

Δ = E[score | high arm ] − E[score | low arm ], and per-puzzle verdicts are aggregated to a principle-level verdict. 

a) Predictability gate: For each puzzle, we fit a Light-GBM regressor on the training-split workflows (200 trees, learning rate 0.05, 31 leaves, min_child_samples = 10, fixed seed) predicting score from design features, and evaluate it on the puzzle’s held-out validation workflows. A puzzle is admitted iff validation 𝑅 2 > 0.05 and Spearman 𝜌 > 0.30. Both are required: a constant predictor attains 𝑅 2 = 0 with undefined 𝜌 ,while a rank-preserving but magnitude-compressing predictor attains 𝜌 > 0 with 𝑅 2 ≤ 0, so the conjunction enforces both calibration and ranking (see § I). 

b) Feature-set for the predictability gate: The predictabil-ity gate is parameterized by the feature set supplied to the regression surrogate, since the admission of a puzzle is meaningful only if the surrogate has access to features of the type the candidate principle concerns. A puzzle whose validation 𝑅 2 exceeds the gate threshold under a feature set that includes prompt-length statistics provides no evidence that its score variation is explained by structural design choices; conversely, restricting the surrogate to structural features alone risks excluding puzzles whose design signal is real but weaker than a prompt signal. We build the feature set using both handcrafted features that leverage the actual execution code of the workflows, associated external prompt files, and features that were extracted during AutoResearch explorations.

C. AFlow Integration 

The AFlow codebase [33] was modified along three axes. First, the operator registry was replaced with the six primitives of §C-A, with corresponding updates to the optimizer-facing operator manual injected into the modification prompt (§D-D). Second, the dataset adapter was extended to interface with the Enigmata generators and verifiers; this required matching Enigmata’s per-puzzle scoring contracts to AFlow’s evaluator interface and routing the difficulty-bundle parameter through the existing task-config plumbing. Third, the per-round telemetry was extended to record 1) per-call worker/aggregator role attribution, and 2) the prompts emitted by the optimizer for each instantiation. 

D. Enigmata Specification 

Enigmata [3] bundles 36 abstract-reasoning puzzles, each paired with a parametric generator and a deterministic, rule-based verifier. The verifier performs an exact match against canonicalized ground-truth output and admits no partial credit, with the per-instance score ∈ { 0, 1}. We restrict our experiments to the 30 puzzles for which both generator and verifier expose programmatic interfaces; the remaining six puzzles are excluded. Difficulty bundles are inherited from the Enigmata partition, which was calibrated against GPT-4o pass rates [3]: 27 of the 30 retained puzzles expose the full {Easy , Medium , Hard }

bundle, while three (Hitori, LightUp, and TicTacToe) expose only {Medium , Hard }.For each (puzzle, bundle) cell, we sample 𝑀 = 20 instances at search initialization and reuse this fixed set across all 

𝐾 = 5 AFlow searches and all workflow rounds within a search. Reusing instances within a cell ensures that score variation across workflows reflects workflow structure rather than instance resampling. Mixed-difficulty bundles are left to future work. The category breakdown of the different puzzles is reported in Table XIV. 

E. Filtered Puzzles and Failure Modes 

Of the 30 retained puzzles, four (EightPuzzle, NinePuzzle, FifteenPuzzle, and SixteenPuzzle), all in the Sequential cate-gory, were excluded from the analysis corpus. On these puzzles, the maximum score across the entire set was 0: no workflow ever produced a verifier-accepted solution at any difficulty level. Inspection of representative completions confirmed that the failure mode is uniform across operators and difficulty bundles, with the worker model either emitting an incorrect move sequence or asserting that no solution exists. Because admission to the predictability gate requires non-degenerate score variance within a puzzle, these four puzzles cannot contribute to any per-puzzle effect-size estimate; retaining them would inflate 𝑛 total without adding statistical power. The filtered analysis corpus therefore comprises 26 puzzles and 28 ,568 workflows (Table IX). A secondary failure mode, applying to the executable-workflow filter rather than to whole puzzles, removed 1 ,031 workflows (3 .0% of the post-bundle corpus) for which the AFlow Optimizer produced a graph that could not be evaluated, 13 typically because a custom prompt referenced an undefined placeholder or a deleted prompt key. These failures are uniformly distributed across the (puzzle, bundle, model) grid and do not bias the structural feature distribution conditional on successful execution. A. Feature Engineering and Models 

The feature set 𝒂 = 𝜙 (𝑊 ) is computed only from the workflow’s own source – the operator graph and the prompts – plus the two allow-listed problem-side descriptors (puzzle family and difficulty bundle). The shared operator library, while readable as a reference, is identical across every workflow and therefore cannot produce a feature. The base parsers cover counts and structural summaries of operator calls, prompt-length statistics, placeholder topology, and a handful of style markers (step-by-step, format blocks); the autonomous loop iterates on them. 

a) Train / val / test split provenance: The three-way split is assigned at the level of the AFlow search , not the workflow. Each search is identified by a stable hash of its full configuration; the assignment is deterministic per hash with a fixed seed (so a re-run on the same configuration lands in the same split), and the corpus-flattening step only inherits this assignment without resampling. After flattening, every workflow lives at a content-free identifier workflow_id =

sha1 (search_hash : round ) [ : 16 ]; the legacy (task, round, search_hash) path components are removed from the directory structure, and the two task-/round-dependent imports inside each workflow’s graph source are rewritten to neutral, content-free forms. Together, these guarantee that the workflow source is independent of its on-disk path. The reproducibility contract on the loop is stronger than just split determinism: on any commit, re-running the analysis script after the flattening step must reproduce the committed findings snapshot and the structured metrics record byte-for-byte. This is enforced through pinned random seeds inside every random-state-bearing step of the regression pipeline, a frozen dependency environment, and a prohibition on machine-local state beyond the workflow corpus and a single targets cache. 

b) Identifier exclusions: The row-level identifiers (workflow_id , round index, configuration hash) are forbidden as features, including in any reconstructed or hashed form. The split column itself is also forbidden. 

c) Target-derived feature exclusions: No feature may depend on the primary target 𝑚 or on the workflow’s total cost on any row. This prohibition extends to target encoding of categoricals (smoothed or otherwise), per-group target aggregates, residuals, ranks, and label-derived difficulty priors. A label-derived feature is, by construction, never a property of the workflow’s design. 

B. AutoResearch Details 

Every iteration of the autonomous loop atomically commits, alongside the analysis script, a fixed set of artifacts that together render any past iteration replayable from the git history alone: 

• metrics.json : structured metrics, feature names, and top coefficients (the time-series source for Fig. 7); 

• feature_names.json : the active feature list as a flat array; 

• train.py : the training script driving feature engineering and surrogate fitting. The fitted model and preprocessor binaries are written outside the git tree and overwritten on each run; checking out a past commit and re-running the analysis script regenerates them, and serves as the byte-for-byte reproducibility check. 

a) Per-commit log: A per-commit log table accompanies the artifacts and functions as the running lab notebook of the autonomous loop. Every attempt, whether accepted, discarded, or aborted by a runtime error, appears in this log because the branch is append-only by construction. The verdict labels are the agent’s own classification, recorded at the time of commit; they are included as a reproducibility artifact rather than a primary result, and are not used as features by the surrogate. 

C. Caveats and Mitigated Failure Modes 

The combination of an LLM-driven feature proposer and a sandboxed evaluation loop is, by construction, susceptible to feature constructions that exploit incidental dataset structure rather than workflow design. Two failure modes were observed during early AutoResearch runs and addressed before the design principles reported were finalized. 

a) Round index as a feature: An early proposal used the AFlow round index as a direct numerical feature, exploiting the fact that later-round workflows tend to be selected from higher-scoring parents and therefore inherit a positive score correlation that is unrelated to architectural design. The mitigation strips the round index from the feature-side metadata exposed to the feature-mining loop and restricts the available artifacts to the Python implementations of the workflows. The round index is retained in evaluation metadata for analysis bookkeeping but is never visible to 𝜙 .14 b) Train-mean leakage: A second early proposal com-puted the mean training-set score per (puzzle, bundle) cell and added it as a feature on the validation and test rows, yielding spuriously high 𝑅 2. The mitigation extends the sandbox prompt with an explicit prohibition on aggregate statistics derived from the target column, regardless of split.

B. Cluster-Robust Inference and Small-Cluster Coverage 

The per-cell confidence intervals reported in §V-B and in Tables V–VII are computed using cluster-Wald standard errors with the AFlow search identifier as the clustering unit. Clustering at the search level rather than at the workflow level is the appropriate choice: workflows generated within the same MCTS trace are not independent draws from the workflow population, since the optimizer conditions each expansion on the score history of its parent. The cluster-Wald estimator is consistent in the large-cluster-count limit, with standard recommendations requiring at least 𝐺 ≥ 15 clusters per arm for nominal coverage. 

a) Train-split cluster support: On the training split, per-arm cluster counts across the cells in Tables V– VII range from 19 to 47. A single contrast (TicTac-Toe × op_SharedMemory_count ) sits at the lower bound with 

𝐺 = 19 clusters in its smaller arm; all other train-side contrasts have 𝐺 ≥ 24 per arm. The train-split CIs therefore lie within the regime in which cluster-Wald inference is well-supported, and the train-side strict-sign verdicts ( 𝑘 +/𝑘 − ) are unaffected by the issue described below. 

b) Test-split cluster support: The held-out test split is, by construction, more sparsely supported at the cluster level: the search-level split assigns each AFlow search to exactly one of train, validation, and test, and the test split contains ∼ 15% of searches. Across the cells reported in the test columns of Tables V–VII, per-arm cluster counts range from 4 to 14, with the majority of cells below 𝐺 = 10. The least-supported cells, both with 𝐺 = 4 per arm, would fall outside the asymptotic regime.
